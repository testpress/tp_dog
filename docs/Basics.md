# Observability & OpenTelemetry Fundamentals

This document provides a foundational introduction to **Observability**, **OpenTelemetry (OTel)**, and the core prerequisites necessary to understand distributed tracing, metrics, and application performance monitoring (APM).

---

## 1. What is Observability?

**Observability** is a measure of how well the internal states of a system can be inferred from knowledge of its external outputs (telemetry data). 

In software systems, observability allows engineering and operations teams to answer not just *"Is the system working?"* (traditional monitoring), but *"Why is the system behaving this way?"* (debugging unknown-unknowns, root cause analysis, performance bottlenecks).

```text
Monitoring (Known-Unknowns)       Observability (Unknown-Unknowns)
┌──────────────────────────────────────┐      ┌──────────────────────────────────────┐
│  - "Is CPU usage > 80%?"             │      │  - "Why did P99 latency spike for    │
│  - "Is error rate > 1%?"             │  vs  │     checkout after the last release?"│
│  - Pre-defined dashboards & alerts   │      │  - "Which downstream database query  │
│                                      │      │     is stalling user request #1234?" │
└──────────────────────────────────────┘      └──────────────────────────────────────┘
```

## 2. The Three Pillars of Observability

Telemetry data generated by modern applications is broadly categorized into three core pillars:

```text
                         ┌─────────────────────────┐
                         │   Observability Pillars │
                         └───────────┬─────────────┘
             ┌───────────────────────┼───────────────────────┐
             ▼                       ▼                       ▼
    ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
    │     Traces      │     │     Metrics     │     │      Logs       │
    │ (Request Flow & │     │ (Aggregated     │     │ (Discrete Event │
    │    Waterfall)   │     │   Measurements) │     │    Records)     │
    └─────────────────┘     └─────────────────┘     └─────────────────┘
```

### A. Traces
- **What they represent**: The complete end-to-end journey of a request as it flows through processes, middleware, views, database queries, cache operations, and external API calls.
- **Why they matter**: Traces provide exact execution timelines, parent-child execution hierarchies, and per-operation latencies. They isolate the exact function or query responsible for a slowdown.

### B. Metrics
- **What they represent**: Numerically aggregated values measured over fixed time intervals (counters, gauges, histograms).
- **Key Metric Frameworks (RED & USE)**:
  - **RED Method** (for request-driven services):
    - **Rate**: Requests processed per second (RPS / Throughput).
    - **Errors**: Number of failing requests (Error Rate / 5xx count).
    - **Duration**: Time taken by requests (Latency percentiles: P50, P90, P95, P99).
  - **USE Method** (for resources): Utilization, Saturation, and Errors.

### C. Logs
- **What they represent**: Discrete, timestamped, textual records of events that happened at a specific point in time (e.g. `User 42 logged in`, `Connection reset by peer`).
- **Trace Correlation**: Modern observability connects logs to traces by injecting standard `trace_id` and `span_id` headers into log records.

## 3. What is OpenTelemetry (OTel)?

[**OpenTelemetry**](https://opentelemetry.io) (often abbreviated as **OTel**) is an open-source, vendor-neutral observability framework under the **Cloud Native Computing Foundation (CNCF)**.

### Why OpenTelemetry?
Before OpenTelemetry, each observability vendor (such as Datadog, New Relic, Dynatrace) required proprietary SDKs and custom agents. This led to high vendor lock-in.

OpenTelemetry provides a single, standardized, open protocol for generating and collecting telemetry across all languages and frameworks. You instrument your application once using OTel standards, and you can route that data to any backend (Tempo, Prometheus, Jaeger, Datadog, Grafana Cloud, etc.).

```text
┌─────────────────┐
│   Application   │
│   (TraceNest)   │
└────────┬────────┘
         │ OTLP / HTTP (Standard OpenTelemetry Protocol)
         ▼
┌─────────────────┐
│ OTel Collector  │ (Processes, batches, extracts spanmetrics)
└────────┬────────┘
         ├────────────────────────┬────────────────────────┐
         ▼                        ▼                        ▼
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│  Grafana Tempo  │      │   Prometheus    │      │  Other Backends │
│ (Trace Storage) │      │(Metrics Storage)│      │(Datadog/Jaeger) │
└─────────────────┘      └─────────────────┘      └─────────────────┘
```

## 4. OpenTelemetry Architecture & Key Concepts

### 1. API vs SDK
- **OpenTelemetry API**: Defines the abstract programming interface used to instrument application code (e.g., `get_tracer()`, `start_as_current_span()`). The API has zero runtime dependencies and does nothing unless an SDK is registered.
- **OpenTelemetry SDK**: The concrete implementation of the API. It manages tracer providers, samplers, span processors, batch queues, and exporters.

### 2. TracerProvider & Tracer
- **`TracerProvider`**: The central factory and state container that manages tracing configuration, resource metadata, samplers, and span processors.
- **`Tracer`**: An object obtained from the provider (e.g., `get_tracer("my-tracer")`) used to create and start individual spans.

### 3. Resources
A **Resource** captures static metadata about the entity producing telemetry (e.g., service name, environment, cluster, host, version).

Common standard resource attributes:
- `service.name`: The identifier for your microservice (e.g. `order-service`).
- `deployment.environment.name` or `deployment.environment`: Deployment tier (e.g. `production`, `staging`, `development`).
- `service.version`: The semantic release version (e.g. `1.2.0`).
- `service.instance.id`: A unique instance identifier (e.g., hostname and process ID).

## 5. Distributed Tracing Concepts

### Anatomy of a Trace & Span
A **Trace** is a Directed Acyclic Graph (DAG) of **Spans**.

```text
Trace (Trace ID: 4bf92f3577b34da6a3ce929d0e0e4736)
 │
 ├── Span: django.request [SERVER] (Span ID: 00f067aa0ba902b7)
 │    │
 │    ├── Span: django.middleware.SecurityMiddleware (Span ID: 5fb3f0c0b222)
 │    │
 │    └── Span: django.view.ProductDetailView (Span ID: 8a69f5fb33ac)
 │         │
 │         ├── Span: postgres.query "SELECT * FROM products WHERE id = %s" [CLIENT]
 │         │
 │         ├── Span: redis.command "GET cache:product:123" [CLIENT]
 │         │
 │         └── Span: HTTP GET https://api.inventory.internal/stock [CLIENT]
```

### Components of a Span
Each span contains:
1. **Name**: Human-readable operation name (e.g., `django.request`, `redis.command`).
2. **Trace ID & Span ID**: 16-byte and 8-byte hexadecimal unique identifiers.
3. **Parent Span ID**: Identifier of the parent span (empty for the root span).
4. **Span Kind**:
   - `SERVER`: Inbound network requests (e.g., handling an incoming HTTP request).
   - `CLIENT`: Outbound network requests (e.g., making an HTTP call, querying a database or cache).
   - `INTERNAL`: Internal application logic (e.g., view method execution, template rendering).
   - `PRODUCER` / `CONSUMER`: Message broker interactions (e.g., Kafka, RabbitMQ, Celery).
5. **Timestamps**: Exact Start Time and End Time (yielding exact duration).
6. **Attributes**: Structured key-value pairs representing context:
   - `http.method`: `"GET"`
   - `http.status_code`: `200`
   - `http.route`: `"/api/products/{id}/"`
   - `db.system`: `"postgresql"`
7. **Events**: Timestamped annotations representing discrete point-in-time milestones or exceptions:
   - `exception.type`: `"KeyError"`
   - `exception.message`: `"Item not found"`
8. **Status**:
   - `OK`: Operation succeeded.
   - `ERROR`: Operation failed (e.g., unhandled exception or 5xx response).
   - `UNSET`: Default state.

## 6. Context Propagation (W3C Trace Context)

Distributed tracing connects spans across process and network boundaries using **Context Propagation**.

When Service A calls Service B, it serializes its active trace context into standard HTTP headers defined by the **W3C Trace Context** specification:

```text
HTTP Request Headers:
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
              │  └──────────────┬─────────────┘ └──────┬───────┘ └─┬┘
           Version          Trace ID                Parent ID    Trace Flags
                                                                 (01 = Sampled)
```

1. **Incoming Request**: When an inbound HTTP request arrives, the SDK extracts the `traceparent` header.
2. **Trace Continuation**: The root span becomes a child of the incoming remote parent span, continuing the distributed trace seamlessly.
3. **Outgoing Request**: When making downstream HTTP calls (e.g. via `requests`), the SDK injects the current span context into outgoing `traceparent` headers.

---

## 7. Sampling Strategies

High-throughput systems generate millions of spans per second. Storing 100% of traces can be cost-prohibitive. **Sampling** controls which traces are captured and exported.

- **Head-Based Sampling**: The sampling decision is made at the beginning of the trace (when the root span starts) based on rules or probability (e.g. sample 10% of requests via `TraceIdRatioBased(0.10)`).
- **Parent-Based Sampling**: Respects the sampling decision made by the upstream caller in the `traceparent` header.

## 8. Span Metrics: Deriving Metrics from Traces

Instead of instrumenting separate client-side code for metrics and traces, modern architectures use the OpenTelemetry Collector's **`spanmetrics` connector**.

```text
                           ┌────────────────────────┐
                           │      Trace Spans       │
                           │(All operations traced) │
                           └───────────┬────────────┘
                                       │
                                       ▼
                     ┌───────────────────────────────────┐
                     │ OTel Collector: Spanmetrics Engine│
                     └─────────────────┬─────────────────┘
                                       │
                ┌──────────────────────┴──────────────────────┐
                ▼                                             ▼
     ┌───────────────────────┐                    ┌───────────────────────┐
     │  `calls_total` Metric │                    │`duration_bucket` Hist │
     │(RPS & Error breakdown)│                    │(P50, P90, P95, P99)   │
     └───────────────────────┘                    └───────────────────────┘
```

The collector automatically generates:
- **`apm_calls_total`**: Request count by service, endpoint, status code, and error flag.
- **`apm_duration_milliseconds`**: Latency histograms (`apm_duration_milliseconds_bucket`) broken down by route, database query, or Redis command.

## 9. Prometheus Fundamentals & PromQL

**Prometheus** is an open-source systems monitoring and alerting toolkit that stores all data as numerical **time-series**.

### 1. Data Model
Every time-series in Prometheus is uniquely identified by its **metric name** and an optional set of **key-value labels** (dimensions):

```text
apm_calls_total{service_name="course-service", http_route="/api/courses/{id}/", status_code="200"} 452
└──────┬──────┘ └──────────────────────────────────────┬──────────────────────────────────────────┘  └─┬─┘
  Metric Name                                   Labels (Dimensions)                                   Value
```

### 2. Metric Types
1. **Counter**: A cumulative metric that only increases (or resets to 0 on restart).
   - *Example*: `apm_calls_total` (total requests processed).
2. **Gauge**: A metric that can arbitrarily go up or down.
   - *Example*: `postgresql_database_locks` (current active database locks/connections).
3. **Histogram**: Samples observations (usually request durations or response sizes) and counts them in configurable bucket ranges (`le` label).
   - *Example*: `apm_duration_milliseconds_bucket{le="50", http_route="/api/products/"}` (requests taking $\le$ 50ms).

### 3. Essential PromQL (Prometheus Query Language)
PromQL allows real-time aggregation and calculation over time-series data:

* **Rate of Requests (RPS / Throughput)**:
  Uses `rate()` over a moving time window (e.g., `5m`) and aggregates by dimension:
  ```promql
  sum(rate(apm_calls_total{service_name="course-service"}[5m])) by (http_route)
  ```

* **Error Rate Percentage**:
  Computes the ratio of 5xx server errors to total requests:
  ```promql
  (
    sum(rate(apm_calls_total{status_code=~"5.."}[5m]))
    /
    sum(rate(apm_calls_total[5m]))
  ) * 100
  ```

* **P95 / P99 Latency Percentiles**:
  Uses `histogram_quantile()` on duration bucket time-series:
  ```promql
  histogram_quantile(
    0.95,
    sum(rate(apm_duration_milliseconds_bucket[5m])) by (le, http_route)
  )
  ```

### 4. Exemplars: Linking Metrics to Traces
An **Exemplar** is a reference to data outside the metric set — specifically a **Trace ID** attached to a specific metric sample.

When Prometheus records a latency histogram sample, it attaches the active `trace_id`. In Grafana graphs, these appear as **clickable dots** on top of the latency line: clicking the dot instantly opens the exact trace waterfall in Tempo without manual searching.

## 10. Grafana Tempo Fundamentals & TraceQL

**Grafana Tempo** is a high-scale, cost-effective distributed tracing backend designed to store massive volumes of traces using simple object storage (e.g., S3/GCS or local disk).

```text
┌───────────────────────────────┐
│     OTel Collector Exporter   │
└──────────────┬────────────────┘
               │ OTLP / gRPC (Port 4317)
               ▼
┌───────────────────────────────┐
│         Grafana Tempo         │
│  - Ingestion & In-Memory WAL  │
│  - Compressed Block Storage   │
└──────────────┬────────────────┘
               │ TraceQL API (Port 3200)
               ▼
┌───────────────────────────────┐
│      Grafana Flamegraph UI    │
│  Waterfall Span Tree & Timing │
└───────────────────────────────┘
```

### 1. How Tempo Works
- **No Heavy Indexing**: Unlike traditional tracing backends that maintain massive inverted search indices, Tempo stores raw, compressed blocks of spans.
- **TraceQL Engine**: Tempo processes queries using **TraceQL**, a query language tailored for searching and filtering trace trees by attributes, durations, and hierarchical span relationships.

### 2. Essential TraceQL Queries

* **Search by Endpoint and Error Status**:
  Find traces for a specific route where an error occurred:
  ```traceql
  { span.http.route = "/api/orders/{id}/" && status = error }
  ```

* **Find Slow Requests (P99 Outliers)**:
  Find traces where the overall request took longer than 500 milliseconds:
  ```traceql
  { span.http.route = "/api/products/" && duration > 500ms }
  ```

* **Find Traces with Slow Database Queries**:
  Find traces where any downstream PostgreSQL query took longer than 100ms:
  ```traceql
  { span.db.system = "postgresql" && duration > 100ms }
  ```

* **Find Traces Involving Connection Pool (PgBouncer) Queueing**:
  ```traceql
  { span.db.connection.pool = "pgbouncer" }
  ```

### 3. Reading a Waterfall Flamegraph
In Grafana, opening a Tempo trace presents a **waterfall timeline**:
- **Root Span** (`django.request`): Represents the total client-perceived response time.
- **Critical Path**: Highlighted spans that directly account for the wall-clock execution time.
- **Child Spans**: Database queries (`postgres.query`), cache commands (`redis.command`), and outbound calls (`HTTP GET`) show their exact start offset and duration relative to the request lifecycle.
